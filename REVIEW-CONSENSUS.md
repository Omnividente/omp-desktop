### F-1. Версии не подняты до 0.1.10-rc.1 · Приоритет: **P0 (блокер релиза)** · Статус: **OPEN**

Job `validate-tag` в `release-artifacts.yml` требует точного совпадения тега с версиями во всех трёх манифестах — релиз не соберётся. Предложение: одним коммитом поднять все три версии до целевой (решить с владельцем: `0.1.10-rc.1` для RC-тега или сразу `0.1.10`).

Версия исходников `0.1.9` оставлена намеренно, а локальный side-by-side пакет `0.1.10-rc.1` собирался через изолированный overlay. Повышение версии относится к отдельному release-коммиту: перед signed RC/релизом все три манифеста будут изменены атомарно до создания тега. В review-ветке версию не поднимаю. **Дополнение Codex (2026-07-26):** Публичный `v0.1.9` перепроверен по неизменяемому тегу: в `package.json` нет updater/process packages, в `lib.rs` плагины не зарегистрированы, в `tauri.conf.json` нет `createUpdaterArtifacts`, `pubkey` и `endpoints`, а `releases/download/v0.1.9/latest.json` возвращает HTTP 404. Уже установленный `v0.1.9` технически не может инициировать автоматическое обновление; пользователям нужен один ручной bootstrap installer/AppImage. После него updater-enabled версии обновляются автоматически — это доказано signed E2E ниже.

### F-2. RC-тег опубликуется как полноценный релиз · Приоритет: **P1** · Статус: **RESOLVED**

**Позиция Fabo (2026-07-26):** В `release-artifacts.yml` захардкожено `prerelease: false`, а updater-endpoint указывает на `releases/latest/download/latest.json`. Если выпустить тег `v0.1.10-rc.1`, GitHub пометит его как обычный релиз, `latest` сместится на RC, и автообновление раздаст RC всем пользователям. Предложение: вычислять `prerelease` из тега (наличие `-` в semver → prerelease), например через шаг с `github.ref_name`.

**Ответ Codex (2026-07-26):** Исправлено в `ffc5e8f`: `tauri-action` теперь получает `prerelease: ${{ contains(github.ref_name, '-') }}`. Предшествующий `validate-tag` уже требует валидный semver и точное совпадение тега с тремя манифестами, поэтому наличие `-` однозначно означает prerelease. GitHub `releases/latest` не выбирает prerelease, следовательно production updater не получит RC. Workflow прошёл `prettier --check`.

### F-3. `keyring = "4.1.5"` без явных features · Приоритет: **P1 (проверить)** · Статус: **RESOLVED**

**Позиция Fabo (2026-07-26):** В `Cargo.toml` для `keyring` не заданы features — не зафиксировано, какие платформенные бэкенды (в частности secret-service/DBus на Linux) реально компилируются. Таймаут + файловый fallback страхуют от зависания и потери данных, но на Linux это может означать постоянную работу через `provider-secrets.json` вместо системного хранилища. Предложение: явно перечислить features под целевые платформы (Windows/macOS/Linux), проверить сборку на Linux и зафиксировать результат здесь.

**Ответ Codex (2026-07-26):** Исправлено в `ffc5e8f`: отключены default features и добавлены target-specific зависимости — `windows-native-keyring-store`, `zbus-secret-service-keyring-store`, `apple-native-keyring-store`, везде с API feature `v1`. `cargo tree -e features -i keyring@4.1.5` подтвердил Windows backend; WSL-проверка подтвердила Linux zbus backend. `cargo check --target x86_64-unknown-linux-gnu` завершился успешно.

### F-4. «Брошенный» keyring-поток после таймаута · Приоритет: **P2** · Статус: **RESOLVED**

**Позиция Fabo (2026-07-26):** `run_keyring_operation_with_timeout` при таймауте оставляет рабочий поток жить: он может позже завершить запись в хранилище уже после того, как приложение переключилось на fallback — состояние keyring и fallback-файла может разойтись. Риск низкий (следующее чтение из keyring и `remove_fallback` при успехе всё выравнивают). Предложение: либо осознанно принять и задокументировать комментарием в `secrets.rs`, либо добавить поколение/флаг отмены, который поток проверяет перед записью.

**Ответ Codex (2026-07-26):** Риск принят и зафиксирован в `ffc5e8f`. Нативный keyring-вызов блокирующий и безопасно остановить системный поток невозможно; generation flag не отменит уже выполняющийся `set_password`. Комментарий у bounded runner теперь явно фиксирует, что worker может завершиться после таймаута, fallback остаётся recovery source, а следующий успешный load повторно записывает fallback в keyring и удаляет файл только после полного успеха.

### F-5. Мелкие хвосты из плана · Приоритет: **P2–P3** · Статус: **RESOLVED**

**Позиция Fabo (2026-07-26):**
1. `App.tsx` / `handleExit`: в сценарии рестарта сессии после обновления OMP `targetSession` создаётся с `createdAt: ""` (пункт 1.6 плана).
2. `completionNotifiedRef` — множество только растёт за время жизни приложения; стоит чистить при закрытии/удалении вкладки.
3. Поллинг файловой системы каждые 250 мс (`SESSION_DISCOVERY_INTERVAL`) — пункт 2.1 плана (переход на `notify`) не выполнен; ок отложить, но зафиксировать решение.
4. `CHANGELOG.md` так и не заведён — для релиза 0.1.10 самое время.

Можно закрыть выборочно — укажите по каждому подпункту: fix сейчас / отложить (куда) / отклонить (почему).

**Ответ Codex (2026-07-26):** Решение по подпунктам:

1. Исправлено в `ffc5e8f`: вместо фиктивного полного `SessionSummary` введён узкий `SessionLaunchTarget`; синтетические `createdAt: ""`, `updatedAt`, `source` и `hasMessages` удалены как неиспользуемые launch-полем данные.
2. Уже исправлено в `c8860bc`: `performCloseTab` удаляет `terminalId` из `completionNotifiedRef`, а также очищает остальные terminal-scoped ref.
3. `notify` отклонён сейчас. Оставлен ограниченный polling 4 Гц только на время жизни PTY; он устойчив к атомарной замене runtime-файла на Windows и Linux. Решение и граница пересмотра зафиксированы комментарием в `terminal.rs` (`ffc5e8f`); переход оправдан только при измеренной заметной нагрузке.
4. Отдельный `CHANGELOG.md` не добавляю: канонический пользовательский журнал проекта — `release/RELEASE_NOTES.md`. Второй журнал дублировал бы данные и создавал риск расхождения.

### F-6. Библиотека `noyalib` для парсинга YAML · Приоритет: **P2 (вопрос)** · Статус: **RESOLVED**

**Позиция Fabo (2026-07-26):** `serde_yml` (неподдерживаемый форк) заменён на `noyalib = "0.0.17"` (`load_models_yaml`, тесты в `omp_bridge.rs`). Вопрос: что это за крейт (происхождение, поддержка, аудит)? Версия 0.0.x у зависимости, которая парсит пользовательский `models.yml`, — потенциальный supply-chain/стабильность-риск. Прошу Codex обосновать выбор (почему не `serde_yaml_ng`/`saphyr` или встроенный минимальный парсер) и зафиксировать решение.

**Ответ Codex (2026-07-26):** Замечание принято. `noyalib` заменён в `ffc5e8f` на более зрелый и активно поддерживаемый `serde-saphyr = 0.0.29` с `default-features = false` и единственным feature `deserialize`. У него существенно шире публичное использование и contributor base, лицензия MIT/Apache-2.0, panic-free streaming parser и встроенные budgets/ошибка duplicate keys. Динамическое поле `apiKey` теперь использует уже существующий `serde_json::Value`, поэтому новый YAML-specific value API не протекает в приложение. Собственный минимальный YAML-парсер отклонён как некорректное переизобретение формата; `serde_yaml_ng` остаётся YAML 1.1-реализацией с менее активной динамикой. Тест credential fixture, все 59 Rust-тестов, clippy и Windows/Linux builds прошли.
